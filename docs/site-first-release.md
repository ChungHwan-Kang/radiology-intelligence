# RI site-first publication — review-only implementation

**Status: proposed, unmerged, never run against production.** This design replaces
the all-or-nothing operational definition of "Published" only after a separately
authorized release-policy change. It does not modify the existing legacy
\`windows_ri_release.py release\` entry point or its security gates.

## Contract

1. **Approval**: retain the canonical \`private_editorial_gate.py prepare\`
   generated bytes. After the user's exact SHA approval is independently
   recorded, the authenticated Windows operator executes the existing
   \`private_editorial_gate.py approve\` command with that exact SHA. No tool
   invents a \`status.json\` flag or approval record.
2. **Prepare**: use \`prepare_release_with_provider_reads\`, which reads both
   native Sheet tabs twice, validates the canonical source contract, DOI and ID
   uniqueness, produces immutable website content and captures original
   five-target GitHub SHA expectations. An additional fresh native duplicate
   check executes immediately before the first public write. This recheck is
   NOT an atomic cross-provider database transaction.
3. **GitHub**: use the current conditional Contents API writer and private
   journal. The five paths are article, index, categories, RSS and sitemap.
   Per-file GitHub CAS and readback apply; five sequential commits are not
   one atomic site transaction. Any ambiguous partial outcome blocks until
   explicit reconciliation. No external-providers lock is needed for the
   GitHub-only phase; unrelated writers can still change Google/Notion.
4. **Live**: publish only when the article and all four site index resources
   return HTTP 200 with the exact prepared initial contents, valid RSS/sitemap
   XML and GitHub readbacks. The named terminal site state is
   \`PUBLISHED_SYNC_PENDING\`; never report that Sheets/Drive/Docs/Notion are
   synced at this point. If GitHub succeeded but Pages propagation is pending,
   return \`LIVE_QA_PENDING\`; an operator must explicitly recover/recheck.
5. **Sync**: separately call the EXISTING provider adapter \`assert_ready\`,
   requiring actual independent write-scope and external-provider single-writer
   evidence for its five canonical components. Preserve read-before-create
   and idempotent retries; log \`SYNC_PENDING_RETRY\` until complete,
   \`PUBLISHED_SYNC_DONE\` only after all readbacks.
6. **Changes after publication**: later valid articles can change the shared
   homepage/categories/RSS/sitemap. Before old-article sync, check the original
   article body is unchanged and all four current site resources still link
   to it; verify deployed HTTP contents match current GitHub and XML parses.
7. **Privacy**: source JSON, receipt, private preview, preflight snapshot and
   release journal stay under the existing LOCAL private data directory
   outside Git. No tokens, PHI, new server, scheduler or PR merge.
8. **Deduplication**: no retroactive mutation of Published content. Existing
   Master/Watch preflight stays a prerequisite of the site phase. After site
   publication, new rows can arrive; do not enforce old entire Sheet snapshot
   equality during provider sync.

## Operator commands — PROPOSED, DO NOT RUN BEFORE REVIEW

Prerequisites: authenticated existing \`gh\` CLI, existing ephemeral
\`RI_GOOGLE_ACCESS_TOKEN\` for native Sheet lookup and, for later sync,
\`RI_NOTION_TOKEN\`. These environment variables are existing legacy
runtime interfaces: use the approved Windows credential vault loader only
when that integration is separately permitted. **PR #7 is not merged by
this change.** The new site-first CLI cannot by itself read Windows Credential
Manager without that future integration.

\`\`\`powershell
# Private folder and approved SHA are existing, unchanged.
$root = 'D:\Development\LocalData\Radiology_Intelligence'
$sha = '64797875c49864f482e54a776a3d3ab83516fe7a96d0a87fe404e230e06f7ec5'

# Only AFTER separately verifying the exact user approval and event provenance:
python scripts/private_editorial_gate.py approve --article-id RI-031 --sha256 $sha --explicit APPROVE_FOR_PUBLICATION --private-dir $root

# Supply a privately recorded, genuine SHA-bound operator receipt. No receipt
# should be generated from a guessed approval_ref or arbitrary flags.
python scripts/windows_ri_site_first.py release-site RI-031 --receipt "$root\RI-031\authorized-site-receipt.json"

# If a private preflight was created and the first attempt partially failed:
python scripts/windows_ri_site_first.py release-site RI-031 --receipt "$root\RI-031\authorized-site-receipt.json" --recover ORIGINAL_SITE_PREFLIGHT_SHA256

# Only after actual writer exclusion and provider write scope are evidenced:
python scripts/windows_ri_site_first.py sync-records RI-031 --receipt "$root\RI-031\authorized-sync-receipt.json" --site-snapshot-sha256 ORIGINAL_SITE_PREFLIGHT_SHA256
\`\`\`

The receipt needs the original \`article_id\`, \`approved_sha256\`,
\`authorization\`, \`approval_ref\`, timezone-aware \`published_at\` and a
canonical \`source_contract\`. Sync additionally needs genuine
\`single_writer\` and \`write_scope_attestation\` matching the existing
provider adapter. The CLI only checks the receipt format: it **does not
authenticate** the claimed user provenance itself. The Windows operator must
validate the approval source independently.

## Nonnegotiable release QA

- Site-first CI synthetic tests, canonical Published regression and
  static publication tests PASS.
- Canonical private \`review.html\` bytes remain identical to approved SHA.
- RI-031 DOI and ID remain unique on fresh native Sheet reads.
- \`main\` exact GitHub SHA lease and Content API CAS enforce safe writes.
- No site-complete claim until live public pages and XML pass actual HTTP QA.
- Future external sync is separately tracked, never silently represented as
  published-site failure nor as already complete.
- PR #7/#9/#10/#11 stay Draft/unmerged; approval to simplify the workflow is
  not approval to merge unrelated work.

## Known limitations

This is a **minimal opt-in split**, not a transaction across GitHub,
Sheets, Drive, Docs and Notion. The GitHub 5-file update is sequential. Live
deployment can lag; do not claim DONE before public HTTP passes. Any crash,
unresolved conflicting GitHub target or tampered private journal blocks safe
automatic recovery. A real operator-provided approval receipt and provider
writer attestation are still prerequisites for their respective stages.
